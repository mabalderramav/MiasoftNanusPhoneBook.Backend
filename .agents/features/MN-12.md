# MN-12 — WebApi: Document the API with OpenAPI (Swagger UI, ReDoc and Scalar)

## Summary

Serve the generated OpenAPI document (`/openapi/v1.json`) through three viewers: **Swagger UI**,
**ReDoc** and **Scalar**. Document every resource endpoint (Agendas, Locations, Profiles, Users,
WorkAreas, Workstations) with a versioned route, group name, tag, **summary**, **description**,
success response type and ProblemDetails error responses.

- **Reference implementation:** `src/MiasoftNanus.PhoneBook.WebApi/Locations/Endpoints/LocationEndpoints.cs`
  (done, except `.WithSummary(...)`)
- **OpenAPI setup:** `src/MiasoftNanus.PhoneBook.WebApi/Extensions/AppOpenApiBuilderExtensions.cs` (done)
- **Pipeline:** `src/MiasoftNanus.PhoneBook.WebApi/Program.cs` (done)

## Motivation

Right now only Locations has descriptions and response types. The other groups show up in the document
untagged, without descriptions and without success schemas (the handlers return `IResult`, so the
generator can't infer the body type). No endpoint has a summary, so the operation lists in Swagger UI,
ReDoc and Scalar show only the raw `METHOD /route`. Front-end developers and testers need one
browsable, accurate contract.

### 2. Summary vs. description

Each operation gets **both**:

| Metadata | OpenAPI field | Where it shows | Style |
|---|---|---|---|
| `.WithSummary("...")` | `summary` | One-line title in the operation list (Swagger UI row, ReDoc/Scalar sidebar) | Short, imperative, no trailing period, ≤ ~5 words — e.g. `Get location by ID` |
| `.WithDescription("...")` | `description` | Detail panel when the operation is opened | Full sentence(s) with period; mention behavior, limits, required headers |

Groups get only `.WithDescription(...)` (tag description); `.WithSummary` is per endpoint.

### 3. Pattern (LocationEndpoints, with summaries added)

```csharp
var locationGroup = app.MapGroup("/api/v1/locations")
    .WithGroupName("v1")
    .WithTags("Locations")
    .WithDescription("Endpoints for managing locations.");
locationGroup.MapGet("/", GetLocationAll)
    .WithSummary("Get all locations")
    .WithDescription("Gets all locations.")
    .Produces<IEnumerable<LocationDto>>()
    .ProducesProblem(StatusCodes.Status404NotFound);
locationGroup.MapGet($"/{{id:guid}}", GetLocationById)
    .WithSummary("Get location by ID")
    .WithDescription("Gets a location by its ID.")
    .Produces<LocationDto>()
    .ProducesProblem(StatusCodes.Status404NotFound);
locationGroup.MapPost("/", CreateLocation)
    .WithSummary("Create location")
    .WithDescription("Creates a new location.")
    .Produces<LocationDto>(StatusCodes.Status201Created)
    .ProducesProblem(StatusCodes.Status400BadRequest);
locationGroup.MapPut($"/{{id:guid}}", UpdateLocation)
    .WithSummary("Update location")
    .WithDescription("Updates an existing location.")
    .Produces<LocationDto>()
    .ProducesProblem(StatusCodes.Status400BadRequest)
    .ProducesProblem(StatusCodes.Status404NotFound);
locationGroup.MapDelete($"/{{id:guid}}", DeleteLocation)
    .WithSummary("Delete location")
    .WithDescription("Deletes a location by its ID.")
    .Produces(StatusCodes.Status204NoContent)
    .ProducesProblem(StatusCodes.Status404NotFound);
```

Rules for every group:

1. Route prefix becomes `/api/v1/<resource>`.
2. Group: `.WithGroupName("v1")`, `.WithTags("<Resource>")`, `.WithDescription(...)`.
3. Each endpoint, in this order: `.WithSummary(...)`, `.WithDescription(...)`, existing behavior
   metadata (`.Accepts`, `.DisableAntiforgery`, size limits), one `.Produces<T>(status)` for the
   success response, then `.ProducesProblem(...)` / `.Produces(401)` for every error.
4. Route templates use `$"/{{id:guid}}"` consistently.
5. Update the URI in `TypedResults.Created(...)` to the new prefix (e.g. `$"/api/v1/agendas/{id}"`).
6. Don't change handler logic, status codes or return types (except the Profiles fix in §5).

| DELETE | `/{id:guid}` | Delete agenda | Deletes an agenda by its ID. Requires the admin `X-Api-Key` header. | 204 | **401**, 404 |

Notes:

- Keep `.Accepts<PatchAgendaDto>(...)`, `.DisableAntiforgery()`, `RequestSizeLimitAttribute` and
  `.WithFormOptions(...)` as they are.
- Upload: add `.Accepts<IFormFile>("multipart/form-data")` if the generated schema doesn't show the
  `photo` form field.
- Photo download: `.Produces(StatusCodes.Status200OK, contentType: "image/jpeg", additionalContentTypes: ["image/png", "application/octet-stream"])`
  (adjust to the extensions the domain allows).
- 401 is plain `TypedResults.Unauthorized()` (no ProblemDetails body) →
  `.Produces(StatusCodes.Status401Unauthorized)`, not `ProducesProblem`.
- `X-Api-Key` comes from `[FromHeader]`, so it already appears in the document as a header parameter.

## Scope

**Changed:** the six resource endpoint files (route prefix, `.WithSummary` + `.WithDescription`,
response metadata, `Created` URIs), the `ProfileEndpoints` `.ToDto()` fix, and the ReDoc route/comment.

**Not changed:** handler logic, domain/application layers, error mapping (`ProblemDetailsHelper`),
status codes, X-Api-Key validation.

**Breaking change:** every resource route moves from `/<resource>` to `/api/v1/<resource>`. Any
client (front-end, Postman collections, `.http` files) must be updated. No test project or `.http`
file in this repo references the old routes.

## Notes / Future Considerations

- Add an OpenAPI document transformer for `Info` (title, version, contact) and an `ApiKey` security
  scheme for `X-Api-Key`, so viewers show an "Authorize" button.
- XML doc comments on DTOs → schema descriptions (`<GenerateDocumentationFile>true</GenerateDocumentationFile>`).
- `.WithName("GetLocationById")` etc. for stable `operationId`s (useful for client code generation).
- Consider `TypedResults` union return types (`Results<Ok<T>, NotFound<ProblemDetails>>`) so metadata
  is inferred and can't drift from the code.
